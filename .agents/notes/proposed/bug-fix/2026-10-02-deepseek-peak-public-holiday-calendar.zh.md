# Agent Note: DeepSeek 峰谷计价需要本仓库没有的中国法定节假日日历

Status: proposed

## Problem

上报的症状是「估算价格约为实际价格 X2」，归因于「调休上班的周末被算成空闲」。调查确认 [峰谷计价记录](../implemented/feature/2026-08-29-usage-peak-pricing-and-announce-fix.md) 里的时钟确有缺陷，但偏差方向与上报相反：估算是**偏低**，出在法定节假日；而周末的处理方式本来就与 provider 的计费口径一致。

官方口径（[api-docs.deepseek.com 定价页](https://api-docs.deepseek.com/quick_start/pricing/)，注 (2)）为：高峰时段是北京时间周一至周五 09:00-12:00、14:00-18:00，**不含中国法定节假日**；其余时段为空闲时段，**包括周末及中国法定节假日全天**。

由此得到两条方向相反的结论：

- **法定节假日的日期无法由任何规则推导。** 国务院每年单独发文安排，日期会变，规则算不出来。已发布的时钟只判 `getUTCDay()`，于是每个周一至周五都算高峰，包括本应半价的节假日上午——这是上报里真正成立的那一半。
- **调休上班的周末不是高峰日。** provider 认日历日而非工作安排：被指定为工作日的周日仍然全天空闲。中文报道在转述 2026-09-19 的说明时明确写道：调休上班的周末与中国法定节假日全天均按空闲时段计费。已发布的 `weekday >= 1 && weekday <= 5` 判据本就与此一致，若按上报改成「调休上班日算高峰」，等于引入一个新的、方向相反的误差。
检索本仓库与 `node_modules` 未发现可离线使用的节假日数据集：没有 `chinese-days`、`workalendar`、`holiday-calendar` 之类包，`pnpm-lock.yaml` 里也没有；`@deepseek-ai/dsh-util-time` 只做 IANA 时区校验与规范化。`src/core/` 内无日历工具。按仓库规则，凭空造表与请求网络接口都不可行。

## Proposal

1. **先落地可由规则推导的一半（即本次改动）。** `deepseekPeriodAt` 与 `deepseekModelSpend` 接受可选的 `PublicHolidayCalendar`（对北京时间 `YYYY-MM-DD` 字符串判断 `isPublicHoliday(date)`），并把高峰判定与下次翻转扫描统一走一个 `isPeakDay()` 谓词。默认为空日历，既有调用方与全部已发布行为保持不变。
2. **保留周末规则原样。** 无论日历怎么说，周六周日都不会成为高峰日。这正是官方口径，对应的那条测试正是防止将来「修复」重新引入上报错误的护栏。
3. **接下来由人决策数据源。** 在那之前估算仍会在节假日窗口高估，README 继续把它写成已知限制，而不是假装估算精确。
4. **数据源选定后接在折叠处**（`src/host/usage-service.ts` 的 `totalsFrom`），让一份日历统管估算；不要把查询散落到计价模块里。

## Context & Efficiency Impact

日历是一个单方法接口、默认取常量，因此 host 半区每次折叠多一次函数调用，浏览器半区在有人传入之前零成本。`YYYY-MM-DD` 字符串是正确的粒度：节假日全天空闲，永远不需要时刻分量。没有 schema、wire 或提示词成本；该接口只在 `src/core/` 内部。

## Alternatives considered

- **按上报把调休上班日当作高峰日。** 依据证据否决：provider 对落在周六周日的指定工作日全天按空闲计费。这样改会让估算离账单更远、且偏到相反方向；而节假日比周末少见，出了错也更难被发现。
- **在包内硬编码 2026（或任意单年）节假日表。** 否决：会静默过期。安排每年重发，过期表比空表更糟——空表是已知且有文档的缺口，过期表则看起来权威。本则提案的接口正是将来经评审的表应当安放之处。
- **运行时从网络接口拉取日历。** 否决：本包是本地台账，浏览器 bundle 纯度门也不允许任意运行时抓取；一个随网络可用性静默变化的估算器不是确定性的成本记录。
- **引入第三方节假日依赖。** 本身不否决，但本次不采纳：目前未安装此类包，新增依赖是维护者的供应链决策，且安装涉及网络，超出本任务授权。
- **由农历推导节假日。** 否决：农历日期只有在国务院给出放假偏移决定之后才映射到公历节假日，那不是规则，而是要维护的第二套日历。

## Acceptance criteria

数据源选定且折叠处传入真实日历后：落在法定节假日内的普通工作日按空闲档计价，节外的同一工作日按高峰档计价，且节假日当天的估算不再与真实账单出现数量级偏差。届时本记录移到 `implemented/`，并由本仓库维护一张经评审的小表，或记录外部数据源与其刷新触发条件。

## Risks

- 在日历接入之前，估算在节假日窗口高估：节假日上午实际半价、估算按全价。用户拿节假日当天的估算对账单时，仍会看到同一个「约 X2」症状，只是归因正确了。
- 错误的表比没有表更糟：把普通工作日标成节假日的日历会让繁忙的一天被低估。将来任何表都需要一条「已知普通工作周不受影响」的测试。
- 默认空日历的行为意味着这个缺口在测试里不可见；忘记传入日历的调用方拿到的是一个看似合理但错误的数字，而不是报错。
