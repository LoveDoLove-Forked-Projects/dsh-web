# Agent Note: 任务看板调度具备计划类型与持久化次数预算

Status: implemented

## Problem

看板的定时规则原本只有循环 cron 一种。规则可以启用、停用或改时区，却无法表达
「在未来某个时刻只执行一次」，也无法表达「最多执行 N 次」：

- 一次性只能写成日期限定的 cron（钉死某一天的年度规则），卡片之所以不再复发，
  靠的是执行 agent 事后把它关掉。这不是一次性调度，而是「循环 + agent 配合」：
  agent 失败、被打断或干脆没照做，卡片就会留到明年继续触发。
- 有限次请求（「执行两次」）没有任何原生停止点，调度会一直触发，直到有人手动关闭。
- 规则没有计数器，所以「已经执行几次」只能从执行历史里猜——历史会被裁剪、把手动
  执行算进去，也分不清「调度触发」与「人工执行」。

看板自己的 Host 账本就是看板执行的权威调度器：既有笔记已经否决过把这件事交给
宿主级 schedule 服务——那个服务调度的是会话而非看板级联，也不了解账本、权限门与
run group（[原生面板与计时器](../architecture/2026-09-25-task-board-native-panel-and-timer.md)、
[调度时区](2026-09-29-task-board-schedule-time-zone.md)）。因此原生一次性只能
落在看板自己的调度器里。

## Decision

一条规则描述两种计划之一，并自带次数预算。

### 规则

`ScheduleRule` 增加一个存储的计划判别与计数器：

- `mode: 'cron' | 'once'`。字段出现之前写入的账本规则一律规范化为 `cron`，
  历史卡片因此保持原有复发行为。
- `cron?: string` 变为可选，只出现在 `cron` 规则上；`at?: number` 保存
  `once` 规则的唯一计划时刻，执行后仍保留，详情页因此仍能显示计划墙上时间。
- `runCount: number` 是预算计数器。`maxRuns?: number` 给循环规则设上限
  （缺省即不限次数，保持历史行为）；一次性规则隐含预算 1，不存上限。
- `endedAt`/`endedReason` 记录规则自行停止，`skippedAt`/`skippedReason`
  记录最近一次没有产生执行的触发。两者都是稳定的原因码（`fired`、`limit`、
  `no-target`、`missed`、`busy`、`permission`），绝不存展示文案：看板经
  自己的语言字典渲染。

一次性计划的时刻是 `at`；调度目标 `nextRunAt` 在规则启用期间等于它，用尽后
清空。一次性不会被写成任何 cron 表达式。

### 计次语义

**计数器只按调度器成功开启的执行次数递增，别的都不算。** 具体地：

- 手动 `run`/`rerun` 绝不触碰 `runCount`；只有到期触发路径会。
- 权限绑定未确认、卡片已有在跑执行、计划已无可达时刻、触发时刻落在看板未运行
  期间，一律不消耗次数：该次触发被跳过、预算不变，原因记在规则上。
- 账本已经开启执行、随后启动失败的一次触发仍然消耗一次：执行记录确实存在
  （结算为失败），这正是「创建了一次执行」的含义。失败绝不自动补跑，因此也
  不可能把规则推过上限。
- 结算结果从不移动计数器：所以「跑了两次都失败」就是两次预算里的两次，而不是零次。

### 预算的执行位置

闸门放在账本这个唯一写入者内部：`HostTaskLedger.openScheduled` 对已用尽预算的
规则拒绝开启任何执行，它真正开启的那次与计数写在同一笔原子提交里。因此过期
定时器、重复触发、手改账本与重启都无法超额。下一触发点由账本计算而不是由
service 传入，所以「下次何时到期」只有一个事实源。

恢复沿用既有「错过的触发只跳过、不补跑」契约；对一次性有一处特定结果：在看板
未运行期间错过时刻的一次性规则以 `missed` 停止（它没有后续可滚动），循环规则
则向前滚动并记录跳过。

### 持久化、协议与界面

- 账本 schema 升到 v6。v2/v3/v4/v5 文档无损迁移；模式/计数/停止字段由规范化解析
  补齐，Host 时区仍只盖给早于「存储时区」的那些代际。
- `set-schedule` 与创建时 `schedule` 接受 `mode`、`at`、`maxRuns`；严格
  线上闸门拒绝小数时刻、非正或小数上限与未知模式，过去时刻由持有 `now` 的
  use case 拒绝。导入路径校验同一形状，不可用规则被丢弃而不是丢掉整行任务。
- `task_board_schedule` 增加 `mode`、`at`、`maxRuns`（`0` 表示清空上限回到
  不限次，与空字符串清时区的约定一致），其视图报告计划类型、计数、上限与
  停止/跳过记录。
- 任务详情与新建对话框提供计划类型、一次性用的带时区 `datetime-local`、
  次数上限选项（不限/1/2/自定义），以及规则自身状态：下次触发、
  `runCount`/上限、剩余次数、如何结束、最近跳过什么。详情页另有显式取消，
  卡片徽章对一次性显示「单次」。
- 重新启用已停止的规则、或切换计划类型，会开启新预算并清空停止记录；编辑
  在跑规则的表达式、时区或上限则保留已消耗计数，因此已花完的预算绝不会被
  静默重置。

## Alternatives considered

- **继续用日期限定的年度 cron 加执行 agent 自行关闭来充当一次性。** 否决——
  它不是一次性：agent 失败或被打断时规则仍然启用，并且把调度的正确性绑在
  被执行的工作上。需求恰恰是系统自己停止，而不是 agent。
- **计数不落库，直接从执行历史推导。** 否决——历史只保留最近 20 条，包含手动
  执行与重跑，也无法区分调度开启的执行与人工执行，推导出的预算会漂移，甚至
  被一次裁剪重置。
- **卡片正在运行时，一次性改用重试而不是跳过。** 本次否决——看板既有契约就是
  已运行卡片跳过当次触发，而重试会在一个任意更晚的时刻、以针对原时刻解析的
  ACL 启动工作。该取舍记录在 Consequences 中；改变它应当是一次显式的后续
  决定，而不是副作用。
- **有限次规则在进程内循环（触发 N 次后停）而不持久化计数。** 否决——重启会
  忘记计数并可能超过上限，正是需求点名的失败。
- **把看板调度交给宿主级 schedule 服务。** 与上述两篇 owning note 同样否决：
  那个服务投递的是会话后续消息，既没有看板账本，也没有权限门与级联 run group。

## Consequences

- 「在此刻只跑一次」成为一个存储事实：规则恰好开启一次执行并在同一笔提交里自行
  停用，之后任何触发、刷新或重启都不会产生第二次。
- 有限次规则在自己的计数处停止。执行 agent 无论成功、失败还是无视提示，都无法
  延长或缩短它。
- 计数可见且持久：刷新或重启后 `runCount`/上限仍在，看板报告规则如何结束或
  最近跳过了什么。
- 被错过的一次性计划是终态的，绝不补跑。计划时刻卡片恰好在运行、或看板整段
  停机，都会失去这一次触发；规则显示 `missed` 或 `busy`。这是把既有跳过契约
  延伸到没有下一次的计划，也是用户可能更期待重试的唯一一处。
- 调度已开启但启动失败的运行，仍然消耗预算中的一次。这是按「创建执行」而非
  「执行成功」计数的直接结果。
- 重新启用已停止的规则会重置预算。用户重新启用这一动作本身换来新一轮，而
  「已结束」的展示让上一轮的计数在这之前就已可见。

## Testing

- `tests/schedule-once.spec.ts` 以固定时钟驱动账本：一次性计划校验（过去/相等/
  小数时刻、上限取值）、一次性恰好开启一次执行并自行结束、花掉的一次性刷新后
  不再触发、被错过的一次性跳过且不消耗、两次上限在两次后停止（结算不移动计数、
  后续触发不再开启）、部分消耗的预算跨重启保留、忙跳过不消耗、手动执行不消耗。
- `tests/host-service.spec.ts` 触发可控的 `HostTimerFace`：一次性按精确延迟
  布防、只触发一次且不再有定时器；两次上限跨两次定时触发后不再布防；停机期间
  到期的一次性在启动时被跳过；调度启动失败的那次恰好消耗一次预算且不会被提前重试。
- `tests/tasks.spec.ts` 与 `tests/store.spec.ts` 覆盖规则转换与 v6 修复
  （无时刻的一次性被丢弃、计数与停止记录往返）。`tests/host-ledger.spec.ts`
  覆盖迁移与到期引用投影。`tests/protocol.spec.ts` 覆盖 set-schedule、创建时与
  导入的线上闸门。`tests/agent-tools.spec.ts` 覆盖工具参数。
  `tests/schedule-zone.spec.ts` 覆盖带时区 datetime 辅助（含春季跳变空洞）与
  预算/停止文案，`tests/task-detail-edit.spec.tsx` 渲染详情编辑器：切换到一次性
  会持久化解出的时刻、选择上限会写入、花掉的规则会渲染计划时刻与结束状态；
  `tests/new-task-run.spec.tsx` 渲染新建对话框并固定两种创建载荷：带解出时刻的
  一次性计划，以及带自定义次数上限的循环计划。
