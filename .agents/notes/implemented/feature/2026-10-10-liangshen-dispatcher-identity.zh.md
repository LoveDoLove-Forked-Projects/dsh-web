# Agent Note: 梁神模式可追加调度者规则集

Status: implemented

在 persona 内容上延续 [V4.1 Flash 原生重建](2026-09-16-liangshen-v41-flash-native-rebuild.md)，在工作纪律上延续[有界检查与收敛](2026-09-18-liangshen-bounded-inspection-convergence.md)：两篇的决定都保持有效，追加块与它们组合而不是取代任何一方。

## Problem

梁神 persona 刻意极简：一行身份，加上几条固定工作纪律。这个形态对「自己干活的会话」是划算的，对一个职责是驱动其他会话的会话则是错的形态。调度者必须先判定任务多大再动手，先判定同伴是 teammate 还是 subagent 再派发，交出带边界与验收标准的任务书，拿证据核对回报而不是听自我陈述，并且清楚自己的授权到哪里为止。这些都无法从一份从不提派发的纪律里推出来，任其临场发挥的会话每次都会发明一套不同的流程。

那套流程已经存在、经过评审并被写下来，就在订阅仓数据面的独立 dispatch 预设里：【角色识别】段（告诉子代理哪些规则不落到它头上）、【调度者身份】段、R0 到 R8 含 R-T，以及结尾的【反模式】清单。在本地重推一份更短的版本，等于为同一件事再造第二套会分叉的流程。

## Decision

梁神 Config 新增布尔字段 `dispatcher`（schema 默认 `true`，与其余塑造预设的字段一样 `volatile()`），经 `applyPresetOverrides` 把 `dispatcher` 键写进所声明预设的 `minimal-prompt` 行——与 `presentation` 写入 `tool-catalog` 的方式完全同构。开启时 `minimal-prompt.mjs` 在工作目录行之后把调度规则块追加到 persona 段；关闭时回到仅含 persona 与工作纪律的形态，逐字节与该开关存在之前一致。

出厂默认开启：全新安装得到的就是本模式的调度能力，而不是一个需要自行发现并打开的隐藏项；设置界面上的开关是把会话退回 persona-only 面的手段。插件自身的兜底默认值与出厂行一致，因此「行上丢了该键」与「激活时未提供配置」解析出同一个值。

- 规则文本放在新的纯文本模块 `presets/liangshen/dispatcher-rules.mjs` 中，导出 `DISPATCHER_RULES`。它从【角色识别】段到结尾【反模式】清单完整照搬参考文本：【角色识别】段、【调度者身份】段、R0、R0.5、R-G、R1 到 R5、R-T、R6、R7、R8，以及十二条反模式。开启该开关的会话跑的正是当初评审过的那套规则，而不是它的本地摘要。
- 只有一段做了适配。模型路由段原本点名属于订阅仓的守卫（`subagentModelAuthorization`）；梁神部署未必带那个守卫，因此该段改为按作用描述它——DSH 自身「子代理」设置里启用的子代理模型授权守卫，默认启用——不再点名某个仓库或某个可能不存在的配置键。其余规则句子一字未改。
- 【角色识别】段之上的身份行（`你由 {{model}} 驱动，工作目录是 {{cwd}}。`）不予携带。它的占位符属于那个预设自己的渲染器；梁神不绑定这些变量，而在文本由 harness 插值的段里留下 `{{...}}` 会让每次请求都抛错。梁神本来就自己追加工作目录行。
- `minimal-prompt.mjs` 引入该常量，并在 `withWorkspaceLine` 中追加，因此顺序由构造决定：persona、它的纪律、工作目录行、然后是追加的规则。两者之间用两行分隔标题（`## Dispatcher rules (a mode-level append)`）隔开，标题点明该块的含义并声明上面的纪律仍然有效，于是这些规则读起来是一段被宣告的追加，而不是又一条 persona 条目。追加是幂等的：已经带有该块的段不再重复追加。
- `dispatcher` 与 `presentation` 正交。该开关只改提示词；工具面由 `presentation` 决定。不因此改动任何工具、任何行、任何仓库插件。
- 出厂 `agent.cordis.yml` 的 `minimal-prompt` 行带 `dispatcher: true`，该行注释写明了语义。键是显式存在而非缺失，这样 overlay 写入的是该行本就声明的键——与 `guard`、`tool-catalog` 两行的出厂形态一致。

## Testing

- `packages/dsh-liangshen/tests/minimal-prompt.test.ts` 固定：关闭态逐字节一致（persona 段等于 persona 加工作目录行、段列表不变、组装出的段里不出现任何调度文案）；开启态（追加的文本恰为分隔标题加 `DISPATCHER_RULES`、persona 纪律仍在其之前、段列表不变）；规则覆盖完整（【角色识别】、R0 到 R8、R-T、反模式清单齐备）；文本中不含订阅仓名称、不含未绑定的 `{{...}}` 占位符；经 harness 渲染器渲染；无 cwd 的会话；幂等性；追加块从不落进 `workspace-instructions` 段。
- `packages/dsh-liangshen/src/composition.test.ts` 固定：出厂行（shipped `agent.cordis.yml` 中确实带 `dispatcher: true`）；未设置 `dispatcher` 时不写任何键；提交 `true` 时写入该键且该行其余键不动；`tool-catalog` 与 `guard` 两行不移动。
- `packages/dsh-liangshen/src/index.test.ts` 固定 schema 默认值与 volatile 引用，以及 `presentation` / `dispatcher` 的每种组合彼此独立解析。
- `packages/dsh-liangshen/tests/preset-composition.test.ts` 在既有配置键之外固定出厂行的 `dispatcher: true`。

## Alternatives considered

- **只携带精简版调度规则。** 否决。梁神的极简 persona 哲学与约九十行的追加确实存在张力，短版本在上下文预算上是更便宜的答案。它在另一个轴上输了：这些规则不是写作风格指南，而是一套相互咬合的流程。R2 的路由判定是 R5 任务书所依赖的前提，R6 的两次重派上限才是 R8 兜底有界的原因，反模式清单则是整套东西可执行而非仅供参考的原因。裁剪意味着挑选放弃哪些保证，而裁出来的集合既不是评审过的那套、也不是自洽的短版本——它是没人评审过的第三套流程，恰恰是本决定要避免的分叉。调度模式还有一个自我指涉的风险：一个自己发明派发流程的调度者，正是规则所描述的那种失败。完整规则集因此全量携带，代价付在它该付的地方——该开关是运维者可以关掉的一个键，而退回 persona-only 的会话与开关存在之前逐字节一致。
- **在梁神之外另设一个 `dispatcher` agent preset。** 否决。本模式是一套纪律，不是一个工具面：第二个 preset 会为了一个布尔值的差异而复制组合、guard、分页与设置卡。开关保持一份组合、一个设置面，运维者按会话切换一个字段即可。
- **把规则并进 `agent.cordis.yml` 的 persona `prefix`。** 否决。prefix 是组合读取器解析的块标量；九十行的追加会让出厂 persona 与追加规则在维护者唯一用来查看「本模式说了什么」的文件里无法区分，而且不会给运维者留下开关。开关还保证了关闭态逐字节一致，改 prefix 做不到这一点。
- **把规则改写成英文以匹配预设其余文字。** 否决。参考文本是被评审的产物；翻译等于重开已经定稿的措辞，而周边 persona 本来就按设计混用语言。
- **绑定 `{{model}}` 与 `{{cwd}}` 以便顺带携带身份行。** 否决。`minimal-prompt` 不拥有组装的变量表，而 `{{cwd}}` 会与插件已从会话头追加的工作目录行重复——同一事实出现在两处，任一侧改动就会漂移。

## Consequences

- 开启该开关创建的会话是调度会话：它的交付物是计划、任务书、审查结论与交付说明，派发规则从第一次请求起生效。关闭该开关的会话不受影响。
- 追加块随 persona 段传递，因此是稳定前缀上的提示词文本。开启开关会在会话创建时一次性改变该前缀，此后前缀缓存照常复用；会话中途切换会重新声明预设，下一个会话组装出新的提示词。
- 调度规则假定会话可能并不具备的能力（没有子代理工具、不支持 teammate、没有模型选择开关）。R0.5 与 R2 正是为识别这些情况并降级而写，这也是规则自带可用性探测、而不是依赖部署来保证的原因。
- 梁神自身不带子代理模型授权守卫；希望强制 R2【可用时】分支的部署需在本包之外提供。没有它时，会话观测到的是【不可用时】分支。
- 该开关与 `presentation` 正交，因此两者可自由组合；设置界面把它们呈现为彼此独立的字段。
