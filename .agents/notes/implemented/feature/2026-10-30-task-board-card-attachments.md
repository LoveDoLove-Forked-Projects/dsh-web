# Agent Note: Card attachments for the task board

Status: implemented

## Problem

A task board whose card is only text cannot carry the artifact the work is about. A user who wants a card to read a screenshot, a spec, a log or a data file has no way to hand it over: the card carries a title, a description and a prompt, and the prompt can only quote text the user pastes into it. The obvious workaround — pasting bytes into the prompt — destroys exactly what the attachment is for (a raster image becomes unreadable text, a large file becomes a wall of prose), and it grows the ledger with content the board would then have to carry, redact and freeze as if it were the card's own text.

The Harness already owns the durable answer: the official attachment storage (`ctx.attachments`) validates and commits immutable, content-addressed objects, and the official session prompt accepts an image part. What was missing was the board's own side of that seam: a shape the ledger can hold, a way to move bytes from the browser into the storage, a way to prove what the browser claims about them, and a rule for what an execution does with them.

## Decision

**The ledger holds metadata, never bytes.** `src/core/attachment.ts` defines `TaskAttachment`: the kind (`image` or `file`), the opaque storage identifier, the display name, the exact byte length, the media type, the sha256 digest of the exact stored bytes, and — for an image only — its intrinsic pixel width and height. There is no `addedAt`, no base64, no data URL, no raw byte array anywhere in the ledger. `TaskRecord.attachments?` and `NewTaskInput.attachments` are additive optional fields, so a card written before this feature runs exactly as it did. The ledger schema moves from v6 to v7; every older generation (v2 through v6) migrates losslessly through the existing normalization pass, and a card that never carried attachments defaults to none.

**The display name has exactly one form.** `canonicalAttachmentName` turns whatever was offered into the canonical name: the leaf of any path-like text, every control character (a newline included) turned into a space, whitespace runs collapsed into one space, the result trimmed and bounded, an empty result replaced by a fixed placeholder. The Host canonicalizes the name BEFORE publishing it, and the wire gate accepts only a name that ALREADY IS canonical — so the client and the Host agree on one name, and a payload carrying a path, a newline or a control character is refused rather than repaired. A persisted name is repaired on load instead (the ledger never rejects a card over a name), and an image is verified against the storage's OWN name as well as against its bytes and digest. The name reaches an execution prompt, which is why it must be one line without a path part.

**Strict gates on the wire.** The create and update actions accept an attachment list only when every entry is well formed: the exact key set, a canonical name, a non-negative whole byte length, a lowercased well-formed media type, a 64-character lowercase hex digest, and — for an image — a raster media type with POSITIVE whole pixel counts. The count, the per-item byte cap and the total byte cap are the board's own limits: eight attachments per card, 10 MiB per attachment, 32 MiB per card. A list that repairs to nothing clears the field instead of storing an empty array; an update replaces the whole set, and an explicit null clears it.

**One stored object is claimed once.** The storage is content-addressed, so the same bytes uploaded twice answer with the same identifier. A list carrying that identifier twice would claim one object twice and render two rows for it, so the identifier is deduplicated at every boundary that can produce one: the form stages the same content once, the form's merge keeps the first entry, the wire gate refuses a list with a repeated identifier, and the load repair drops the repeat.

**An image always carries its pixel size.** A record without a positive width and height cannot address the stored object, so the wire gate refuses it, the load repair drops it, and `imageRefOf` refuses it too — a 0x0 reference is never manufactured to fill the gap.

**The deployment's own image budget is honoured.** The official storage publishes `maxImagesPerMessage`, `maxMessageImageBytes` and `maxImageBytes`; the board's own caps stay in force, and the deployment's policy can only lower them. The effective values are published with the snapshot, the form refuses a selection over them, the Host refuses a card over them when it proves the metadata, and the execution refuses one when it resolves the attachments — so an image set over the deployment budget never reaches the prompt admission. Only the images count against that budget: plain files travel as paths and never enter a prompt.

**The legacy import and the agent tools do not accept attachments.** The browser's one-time `import` of `dsh.taskBoard.v1` never carried attachments, so an imported document claiming one is refused outright rather than let past the storage check. The agent tool surface likewise has no attachment parameter: an agent that wants a file uploaded says so in words, and a human uploads it.

**The Host does not believe the client's metadata.** Every attachment an action carries is proved against the official storage before the ledger commits it: an image is read back and compared field by field and by digest, a file is streamed and its digest recomputed. A reference the storage does not know, and a record whose metadata does not match the stored bytes, both refuse the whole action. The in-process capability face, the agent tools and the import path accept no attachments at all, so the only way an attachment reaches the ledger is the verified one.

**The upload path is the board's own, and it is a raw-byte route.** `POST /api/task-board/attachments/upload` takes the bytes as the request body. An image goes through the storage's `validateImage` and `saveImage`, so the declared type is checked against the decoded bytes by the storage itself; a file goes through `saveFileStream`, which never collects the whole file in memory. Both paths measure the ACTUAL request stream against the cap rather than trusting a declared length, and both answer with the metadata the Host computed — the size, the type and the digest of the bytes that actually went in. A body past the cap is refused and therefore never reaches the ledger; the storage SDK does not guarantee that a partially written backend object is cleaned up, so the board promises no such cleanup. `GET /api/task-board/attachments/image?id=` serves an image only when a card of this board references that identifier, so an unreferenced id is not a readable object.

**The browser stages locally and uploads on save.** A picked file is a local preview with its name, size and (for an image) a thumbnail until the card is saved; the upload happens when the card is saved, so an abandoned card leaves no stored object behind. Three input modes feed the same staged list: drag and drop, paste, and the file picker. The drop area is focusable and keyboard-operable (Enter or Space opens the picker), and the button inside it keeps its own activation, so a key press there never opens the picker twice. Object URLs are released when a staged row is removed and when the form closes. The removal controls are disabled while a save is in flight, so the set being submitted cannot race a user edit. The detail view shows the persisted attachments — a thumbnail per image, a name and size per row — and says plainly that removing an attachment drops the reference.

**An edit that changes nothing does not touch the attachments.** The edit form puts the attachments into the patch only when the resulting ordered set differs from the card's current one: a title-only or label-only edit never makes the Host re-read and re-verify the stored objects, and it still works in a deployment whose attachment storage is unavailable.

**Every execution resolves the attachments afresh.** Manual runs, cron occurrences, reruns and reused sessions all resolve the card's attachments again against the storage. An image becomes an image part of the session prompt, placed after the text part. A non-image file becomes a readable host path (`ctx.attachments.fileHostPath(ref)`) written into a read-only attachment section of the prompt that is separate from the handover preamble, so the two kinds of reference stay distinguishable to the reading agent. A file whose path is missing or unreadable fails the run before the prompt instead of being silently dropped, and a card with attachments cannot run in a deployment that serves no attachment storage at all.

**The image capability is preflighted against the actual route.** Before the PROMPT IS QUEUED — the session may already exist at that point — the board asks the official model service about the route the run really uses: the card's pin, or the CURRENT route of a reused session, through `ctx.llm.resolveModelInfo(provider, model)`. A route that declares its input modalities and does not include `image` refuses the run with that reason. A route whose modalities are absent is UNKNOWN and allowed: the official model catalog publishes no modality information, so it cannot answer this question, and refusing on its silence would block every image run. A route the board cannot RESOLVE at all skips this preflight; in that case, and in the unknown-modality case, the official Host check remains the fallback that refuses an image the route cannot read. When the host still refuses the image afterwards, its official attachment error is surfaced readably.

**The failure keeps its class.** An attachment failure is a `TaskBoardAttachmentError` with a stable class, and that class survives the action path: a storage that is unavailable answers 503 on an action exactly as it does on the upload, instead of being flattened into a generic rejected action.

**Attachments freeze with the card content.** An executed or archived card keeps the attachments it ran with, exactly as it keeps the prompt it ran with: the attachment list is part of the content fields the freeze gate covers.

**Removal removes metadata.** The official storage has no deletion API. Removing an attachment from a card, or deleting the card itself, removes the metadata only; the stored object stays where the deployment put it. The interface and the README say "remove", never "delete the file", and the board implements no deletion workaround.

## Required verification

- The attachment record carries exactly the metadata fields and no bytes, no base64, no data URL and no upload instant; a file carries no pixel size.
- Loading a card repairs a malformed attachment list entry by entry, drops an entry past the byte caps, caps the count, and leaves a card without attachments empty; every older ledger generation migrates losslessly to v7 with its card fields intact.
- The wire gate refuses an attachment list with an extra field, a name that is not canonical (a path, a newline or a control character), a malformed digest, a repeated identifier, an image without a positive pixel size or a broken limit; the update action replaces the set and clears it with an explicit null; the legacy import refuses a document that claims attachments.
- The upload route refuses a request without the browser marker, refuses a body past the cap (which never reaches the ledger), answers with the host-computed metadata and its canonical name, maps a storage refusal onto its own class, and answers a typed failure when the deployment serves no storage; the image route refuses an identifier no card references and serves the stored bytes for one that is referenced.
- The verification refuses a reference the storage does not hold, a record whose digest does not match the stored bytes and a record whose name differs from the stored one, accepts a record the storage proves, and refuses a card whose images exceed the deployment's per-message budget.
- An execution sends the image after the text part, injects the file's readable path in a section of its own, refuses a file with no readable path before the prompt, refuses an image route that declares no image input before the prompt is queued, allows a route of unknown modality, judges a reused session by its current route, refuses an image record without its pixel size, refuses a card over the deployment's image budget, and resolves the attachments again for every run.
- The interface stages a picked file without uploading it, uploads on save, accepts the file through drag-and-drop, paste and the file picker, stages the same content once, removes a staged row and a stored row, releases the object URL of a removed row and of a closed form, disables the removal controls while a save is in flight, opens the picker from the keyboard without activating it twice, sends the attachments only when the set changed, and shows the refusal of a refused upload without creating the card.
- The three languages carry the same attachment keys with the same placeholders, and the removal notice says the stored file is not physically deleted.

## Alternatives considered

**Store the bytes in the ledger.** Rejected: the ledger is read, copied and frozen as card content, so base64 payloads would multiply its size, drag every card read into a base64 decode, and put user file content into the one file the board writes with `0600` and hands to the browser. The official storage already exists for exactly this content and already owns validation, content addressing and immutability.

**Let the client declare the metadata and trust it.** Rejected: the browser would then be able to attach a claim the storage cannot produce — a digest of bytes nobody stored, a size that does not match the object. The proof is cheap (one read for an image, one streamed digest for a file) and it is the only thing that keeps the ledger's record a fact rather than an assertion.

**Upload on selection instead of on save.** Rejected: a user who picks three files and then cancels would leave three stored objects that no card references, in a storage that cannot delete them. Staging locally and uploading on save keeps the storage and the board in step.

**Let the model catalog decide whether a route accepts images.** Rejected: the official model catalog publishes no input modalities, so it cannot answer the question; treating its silence as "no images" would refuse every image run, and treating its silence as "images" would remove the check entirely. The model's own declared modalities, read through the model service for the exact route, are the only evidence that can refuse an image.

**Refuse an image run whose route's modalities cannot be read.** Rejected: a route that declares no modalities is unknown, not incapable. Refusing on unknown evidence would block every deployment whose provider does not publish modalities — the majority — while the host's own attachment error already catches a route that turns out to be unable.

**Inject the file path into the handover preamble.** Rejected: the handover preamble carries the card's doc and script references, which are part of the continuation-card contract and are delimiter-escaped against spoofing. The attachment path is a different kind of reference — a host path of a stored object — and folding it into the handover text would make the two indistinguishable to the reading agent. It is its own read-only section instead.

**Offer physical deletion of an attachment.** Rejected: the official storage has no deletion API. A workaround that reached into the storage's own directory would depend on its internal layout, break the moment that layout changes, and destroy an object another card may legitimately reference.

**Trust the client's display name, or repair it at every boundary.** Rejected: the name reaches the prompt, so a name carrying a newline could break out of its line and a name carrying a path could point the reading agent at a directory. Repairing it in several places would let two boundaries disagree about the same object; one canonical form, produced by the Host before publishing and accepted by the wire gate only in that form, keeps the client and the Host on one name.

**Let an image record omit its pixel size and fill the gap at read time.** Rejected: the stored object is addressed by its size, so a record without one addresses nothing; manufacturing a 0x0 would turn a broken record into a wrong read. The record is refused or dropped instead.

**Let the board's own caps stand alone.** Rejected: the official storage publishes a per-message image budget, and a card of eight images can exceed it. The deployment's policy is the one that knows what its own prompt admission accepts, so the board takes the stricter of the two and enforces it when it writes the card and when the execution resolves it.

**Re-verify the attachments on every edit.** Rejected: an edit that changes only the title would then depend on the attachment storage being reachable, for a set that did not change at all. The attachments ride the patch only when the set differs.

## Consequences

- A card can carry up to eight files and images, and an execution reads them: images as prompt image parts, other files as readable paths.
- The ledger grows by a few dozen bytes per attachment and never by the size of the attachment.
- The board keeps working in a deployment that serves no attachment storage: it mounts, and every attachment surface answers a typed "storage unavailable".
- Removing an attachment or deleting a card leaves the stored object in the deployment's attachment storage. That is the storage's contract, and the interface says "remove" rather than promising a deletion.
- A card that carries an image cannot run on a route that declares it cannot read images; the run fails before the session is created, with that reason on the card.
- The agent tool surface cannot attach a file; attachments are a human action.
