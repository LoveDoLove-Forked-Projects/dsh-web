# Agent Note: 任务看板的卡片附件

Status: implemented

## Problem

只由文字组成的任务看板无法携带工作本身涉及的产物。想让一张卡去读一张截图、一份规格、一段日志或一个数据文件的用户没有任何交付途径：卡片只有标题、描述和 Prompt，而 Prompt 只能粘贴用户手打的文字。显而易见的绕法——把字节粘进 Prompt——恰好毁掉附件的意义（位图变成读不懂的文本，大文件变成一堵散文），还让账本多出一份本该按卡片正文那样被裁剪、脱敏与冻结的内容。

Harness 早已拥有持久化答案：官方附件存储（`ctx.attachments`）负责校验并提交不可变、内容寻址的对象，官方会话 Prompt 也接受图片部件。缺的是看板自己这一侧的接缝：账本能存的形状、把字节从浏览器搬进存储的通道、证明浏览器对它所声称内容的办法，以及一次执行该怎么消费这些附件。

## Decision

**账本只存元数据，绝不存字节。** `src/core/attachment.ts` 定义 `TaskAttachment`：类型（`image` 或 `file`）、不透明存储标识、展示名称、精确字节长度、媒体类型、精确字节的 sha256 摘要，以及——仅图片——其固有像素宽高。账本里没有 `addedAt`、没有 base64、没有 data URL、没有任何原始字节数组。`TaskRecord.attachments?` 与 `NewTaskInput.attachments` 都是增量可选字段，因此本功能之前写入的卡片行为完全不变。账本 schema 从 v6 升到 v7；每一个更早的世代（v2 至 v6）都经既有的归一化通道无损迁移，从未携带附件的卡片默认为空。

**线上的门禁是严格的。** create 与 update 动作只在每一条都成形时接受附件列表：精确键集、规范形名称、合式的媒体类型（小写）、64 位小写十六进制摘要，以及——对图片——位图媒体类型与**正的**整数像素尺寸。数量、单件字节上限与合计字节上限是看板自己的限额：每卡 8 个附件、单件 10 MiB、每卡合计 32 MiB。修复后变空的列表清空该字段而不是存一个空数组；update 整体替换该集合，显式 null 清空它。

**展示名称只有一种形态。** `canonicalAttachmentName` 把任何被给出的名字转成规范形：路径取叶子、控制字符（含换行）折成空格、空白串折叠成一个空格、去掉首尾空白并有界长度，空则用固定占位。Host 在发布**之前**规范化名称，线上闸门只接受**已经是规范形**的名称——因此客户端与 Host 对同一个名字达成一致，携带路径、换行或控制字符的载荷被拒绝而不是被修复。已持久化的名字在加载时被修复（账本不会因为一个名字丢掉整张卡），图片还会与存储**自己的**名称比对。名称会进入执行 Prompt，因此它必须是单行且不含任何路径部分。

**同一个存储对象只被认领一次。** 存储是内容寻址的，因此同样的字节上传两次会得到同一个标识。携带同一标识两次的列表会认领同一个对象两次并为它渲染两行，因此每个可能产生重复的边界都去重：表单对同一份内容只暂存一行、表单合并时先出现者胜、线上闸门拒绝带重复标识的列表、加载修复丢弃重复项。

**图片始终带像素尺寸。** 没有正的宽高的记录无法寻址存储对象，因此线上闸门拒绝它、加载修复丢弃它，`imageRefOf` 同样拒绝——绝不补出一个 0×0 的引用来填坑。

**部署自己的图片预算被遵守。** 官方存储公布 `maxImagesPerMessage`、`maxMessageImageBytes` 与 `maxImageBytes`；看板自己的上限继续生效，部署的策略只能把它压低。生效值随快照公布，表单按它拒绝选择，Host 在证明元数据时拒绝超预算的卡片，执行在解析附件时也拒绝——因此超预算的图片集永远到不了 Prompt 入队。只有图片计入该预算：普通文件以路径形式传递，不进入 Prompt。

**旧版 import 与 agent 工具都不接受附件。** 浏览器对 `dsh.taskBoard.v1` 的一次性导入从不携带附件，因此声称携带附件的导入文档被整体拒绝，而不是绕过存储校验。agent 工具面同样没有附件参数：需要某个文件的 agent 用文字说明，由人上传。

**Host 不相信客户端的元数据。** 动作携带的每个附件在账本提交前都要对着官方存储证明一遍：图片读回并逐字段比对加核对摘要，文件流式读取并重算摘要。存储不认识的引用、与存储字节对不上的记录，都会让整个动作被拒绝。进程内能力面、agent 工具与 import 路径一律不接受附件，因此附件进入账本的唯一通道就是这条经过验证的通道。

**上传通道是看板自己的裸字节路由。** `POST /api/task-board/attachments/upload` 以请求体承载字节。图片走存储的 `validateImage` 与 `saveImage`，因此声明的类型由存储自己对解码后的字节判定；文件走 `saveFileStream`，全程不在内存里收齐整个文件。两条路径都按**实际请求流**对上限计量，而不是相信声明的长度；两者都返回 Host 自己算出的元数据——真正写进去的那些字节的大小、类型与摘要。越过上限的请求体被拒，因此**不会进入账本**；存储 SDK 不保证已写入后端的部分对象被清理，因此看板不承诺这样的清理。`GET /api/task-board/attachments/image?id=` 只在本看板某张卡片引用过该标识时才提供图片，因此未被引用的标识不是可读对象。

**浏览器先本地暂存，保存时才上传。** 选中的文件在卡片保存之前只是一份本地预览，带名称、大小（图片还有缩略图）；上传发生在保存卡片时，因此被放弃的卡片不会在存储里留下对象。拖放、粘贴与文件选择器三种输入方式喂进同一份暂存列表。拖放区可聚焦、可用键盘操作（回车或空格打开文件选择器），其中的按钮保留自己的激活方式，因此按在按钮上的键不会把文件选择器打开两次。移除暂存行与表单关闭都会回收对象 URL。保存进行期间移除控件禁用，因此正在提交的集合不会被用户的编辑赛跑。详情页展示已持久化的附件——每张图片一个缩略图，每行一个名称与大小——并明确说明移除附件移除的是引用。

**没有变化的编辑不碰附件。** 编辑表单只在**结果集合与卡片当前集合不同**时才把附件放进 patch：只改标题或只改标签的编辑不会让 Host 重读并重验存储对象，在没有附件存储的部署里也照常保存。

**每次执行都重新解析附件。** 手动执行、cron 触发、重跑与复用会话都会再次对着存储解析卡片附件。图片成为会话 Prompt 的图片部件，排在文字部件之后。非图片文件成为可读宿主路径（`ctx.attachments.fileHostPath(ref)`），写进独立于交接前言的只读附件小节，使两类引用对阅读的 agent 保持可辨。路径缺失或不可读时，运行在 Prompt 之前失败而不是被静默丢掉；带附件的卡片在完全不提供附件存储的部署里也无法运行。

**图片能力按实际路由预检。** 在**Prompt 入队之前**（此时会话可能已经创建），看板通过 `ctx.llm.resolveModelInfo(provider, model)` 向官方模型服务询问这次运行真正使用的路由——卡片钉住的模型，或复用会话**当前**所在的路由。声明了输入模态且不含 `image` 的路由以该原因拒绝这次运行。模态缺席的路由属于未知，因此放行：官方模型目录不发布模态信息，回答不了这个问题，拿它的沉默当拒绝会让每一次图片运行都被挡住。完全**解析不出**路由时这道预检被跳过；此时（以及模态未知时）官方 Host 的检查仍是拒绝读不了图片的路由的兜底。宿主此后仍然拒绝该图片时，官方附件错误会被可读地呈现出来。

**失败保留自己的类别。** 附件失败是带稳定类别的 `TaskBoardAttachmentError`，该类别在动作路径上依然保留：存储不可用在动作上同样回答 503，与上传路由一致，而不是被压成一次普通的动作拒绝。

**附件与卡片正文一起冻结。** 执行过或已归档的卡片保留它运行时携带的附件，正如它保留运行时使用的 Prompt：附件列表属于冻结门覆盖的正文字段。

**移除移除的是元数据。** 官方存储没有删除接口。从卡片移除附件、或删除卡片本身，移除的都只是元数据；存储对象仍留在部署放它的地方。界面与 README 只说「移除」，从不说「删除文件」，看板也不实现任何删除绕路。

## Required verification

- 附件记录恰好只带元数据字段，没有字节、没有 base64、没有 data URL、没有上传时刻；文件不带像素尺寸。
- 加载卡片时，非法附件列表逐条修复，超过字节上限的条目被丢弃，数量被封顶，不带附件的卡片为空；每一个更早的账本世代都无损迁移到 v7，卡片字段保持完整。
- 线上门禁拒绝带多余字段、名称不是规范形（含路径、换行或控制字符）、摘要不合式、标识重复、图片缺少正像素尺寸或越限的附件列表；update 动作整体替换该集合并以显式 null 清空；旧版 import 拒绝声称携带附件的文档。
- 上传路由拒绝没有浏览器标记的请求，拒绝越过上限的请求体（它不会进入账本），返回 Host 算出的元数据与规范形名称，把存储拒绝映射到自己的类别，并在部署不提供存储时回答类型化失败；图片路由拒绝没有卡片引用的标识，为被引用的标识提供存储字节。
- 校验拒绝存储不持有的引用、摘要对不上的记录与名称和存储不一致的记录，接受存储能证明的记录，并拒绝图片超出部署每消息预算的卡片。
- 一次执行把图片排在文字部件之后发送，把文件的可读路径注入独立小节，在 Prompt 之前拒绝没有可读路径的文件，在 Prompt 入队之前拒绝声明不支持图片输入的路由，放行模态未知的路由，按复用会话当前路由判定，拒绝缺少像素尺寸的图片记录，拒绝超出部署图片预算的卡片，并在每次运行时重新解析附件。
- 界面暂存选中的文件而不立即上传，在保存时上传，通过拖放、粘贴与文件选择器接收文件，同一份内容只暂存一行，移除暂存行与已存行，回收被移除行与已关闭表单的对象 URL，保存进行期间禁用移除控件，用键盘打开文件选择器且不被重复触发，只在集合变化时才发送附件，并在上传被拒时展示拒绝且不创建卡片。
- 三种语言携带相同的附件键与相同的占位符，移除说明写明存储的文件不会被物理删除。

## Alternatives considered

**把字节存进账本。** 拒绝：账本会被当作卡片正文读取、复制与冻结，因此 base64 载荷会成倍放大它的体积，把每次卡片读取拖进一次 base64 解码，还把用户的文件内容塞进那个以 `0600` 写入并交给浏览器的文件。官方存储本就为此内容而存在，并且已经拥有校验、内容寻址与不可变性。

**由客户端声明元数据并直接相信。** 拒绝：那样浏览器就能挂上一个存储根本产生不了的声明——没人存过的字节的摘要、与对象对不上的大小。证明很便宜（图片一次读回，文件一次流式摘要），而它是唯一让账本里的记录成为事实而不是断言的东西。

**选中即上传而不是保存时上传。** 拒绝：挑了三个文件又取消的用户，会在存储里留下三个没有任何卡片引用的对象，而那个存储删不掉它们。本地暂存、保存时上传让存储与看板始终同步。

**由模型目录决定路由是否接受图片。** 拒绝：官方模型目录不发布输入模态，回答不了这个问题；把它的沉默当成「不支持图片」会拒绝每一次图片运行，把沉默当成「支持图片」则等于取消检查。模型自己声明的模态——通过模型服务对精确路由读出——是唯一能拒绝图片的证据。

**对模态读不到的路由也拒绝图片运行。** 拒绝：没有声明模态的路由是未知，不是无能力。拿未知证据拒绝会挡住每一个不发布模态的提供方——那是大多数——而宿主自己的附件错误已经能拦住真正无力的路由。

**把文件路径注入交接前言。** 拒绝：交接前言承载卡片自身的文档与脚本引用，属于续接卡片契约并做分隔符转义以防伪造。附件路径是另一类引用——存储对象的宿主路径——混进交接文本会让两者对阅读的 agent 不再可辨。它因此是自己的只读小节。

**提供附件的物理删除。** 拒绝：官方存储没有删除接口。伸手进存储自身目录的绕法会依赖它的内部布局，布局一变就失效，还可能毁掉另一张卡片正当引用的对象。

**相信客户端给的展示名称，或在每个边界各修一次。** 拒绝：名称会进入 Prompt，因此带换行的名称可能越出自己那一行，带路径的名称可能把阅读的 agent 指向一个目录。在多处分别修复会让两个边界对同一个对象给出不同的名字；只有一种规范形、由 Host 在发布前产出、且线上闸门只接受该形态，才能让客户端与 Host 站在同一个名字上。

**允许图片记录不写像素尺寸、读取时再补。** 拒绝：存储对象是按尺寸寻址的，没有尺寸的记录什么也寻址不到；补一个 0×0 会把坏记录变成错误读取。因此该记录被拒绝或丢弃。

**只靠看板自己的上限。** 拒绝：官方存储公布了每条消息的图片预算，八张图片的卡片可能超出它。部署的策略才知道自己的 Prompt 入队接受什么，因此看板取两者中更严的，并在写入卡片与执行解析两处强制它。

**每次编辑都重新校验附件。** 拒绝：只改标题的编辑会因此依赖附件存储可达，而那个集合根本没有变。附件只在集合不同时才随 patch 送出。

## Consequences

- 一张卡片可以带最多八个文件与图片，执行会读取它们：图片作为 Prompt 图片部件，其他文件作为可读路径。
- 账本每个附件只增长几十字节，绝不按附件大小增长。
- 不提供附件存储的部署里看板照常工作：它照常挂载，每个附件面都回答类型化的「存储不可用」。
- 移除附件或删除卡片后，存储对象仍留在部署的附件存储里。那是存储的契约，界面说的是「移除」，而不是承诺一次删除。
- 带图片的卡片不能跑在声明自己读不了图片的路由上；运行在会话创建之前失败，原因写在卡片上。
- agent 工具面无法附加文件；附件是人的动作。
