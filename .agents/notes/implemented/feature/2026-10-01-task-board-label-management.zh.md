# Agent Note: Task board label management

Status: implemented

## Problem

任务的标签是看板上唯一的横切分类：它驱动卡片徽章、顶栏多选筛选，并通过标签的「执行提示」影响之后每一次运行的 Prompt。但标签只能在携带它的卡片上编辑，于是标签行只增不减。一个错别字、两个含义相同的标签、或某次实验留下的标签，会永远留在全账本在用标签的并集里，标签行不断变长，最终不再是筛选器而是一堵墙：二十个标签的看板没法靠点击收窄，而产品里没有任何入口能删掉一个。

## Decision

标签由两条整账本迁移管理，以 `rename-tag` 与 `delete-tag` 协议动作暴露：

- **每次编辑一个事务。** 宿主账本原子地完成整次重写——所有命中的卡片在同一次提交里改写、revision 只前进一次——因此并发读者不会看到改到一半的重命名。纯迁移位于 `src/core/use-cases/task-tag.ts`，由宿主账本与无 transport 的客户端路径共用。
- **重命名到已存在的名字即为合并。** 同时带两个标签的卡片保留目标那一行，于是存活标签的执行提示继续生效；只带源标签的卡片则在新的名字下保留它自己的提示。合并不增加列表长度，因此八标签上限不会被编辑破坏。
- **删除覆盖已归档卡片。** 顶栏标签行取自整个账本（留在归档卡片上的标签会立刻回到筛选行），因此该迁移不理会归档边界。
- **看板的标签行提供入口。** 筛选芯片旁的「管理标签」打开标签管理器：每个在用标签一行，带携带它的卡片数、可就地重命名（输入的字与已有标签同名时会在提交前说明将合并），以及删除——删除走共享确认弹窗，并写明会从多少张卡片上移除。
- **清理是一次经确认的执行，不是后台巡扫。** 对话框里的「清理」一行取一个阈值 `N`（默认 5，可填 1..99），把满足「携带它的任务数小于 `N`、且这些任务全部是已完成或已失败」的标签视为候选。已归档卡片按同一口径计入：归档后已结算的卡片会让它的标签放行，归档后仍未完成的卡片则把它留住。规则只读一个数字——有多少张卡片携带它——不看时间、颜色，也不看标签自己携带的提示。
- **先算候选，再写账本。** 没有候选时这一行只如实说明、不动账本；有候选则打开共享确认框，逐个列出标签与其数量，确认后每次一笔 `delete-tag` 迁移逐个移除。清理不新增线动作，也不新增第二条写入路径：每次移除都是删除按钮执行的那笔整账本、跨归档边界的迁移，因此每个标签的原子性就是账本已有的保证，标签的执行提示随名字一起离开。
- **只有线协议对名字严格。** 协议接受去空格后非空、且不超过标签长度上限的名字，其余一律拒绝；去空格、合并与去重属于用例，因此宿主与遗留的内存看板得到同一结果。

## Constraints

- 与其他看板变更一样由宿主裁决：浏览器提交动作，只反映账本确认的结果。无 transport 的遗留内存看板路径套用同一套纯迁移。
- 标签名就是标签的身份。两张卡片带同名标签时它们本来就是同一个标签，这正是「重命名到已有名字」的含义是合并、而不是冲突解决的原因。
- 不改 schema：标签仍是任务行上的可选 `tags` 字段；最后一条标签被移除的卡片会丢掉该字段，与在卡片编辑器里清空标签完全一致。
- 清理只通过从标签列表里去掉一条来改动卡片：列、文本、钉住的目标与执行记录都保持原样；最后一条标签被移除的卡片会丢掉 `tags` 字段，与手动删除完全一致。

## Testing

`tests/task-tag.spec.ts` 覆盖两条迁移（全账本重命名、合并保留目标提示、只带源标签时源提示保留、删除覆盖归档卡片、最后一条标签清空字段，以及未知/空白/超长名字的拒绝与输入去空格）。`tests/tag-manager.spec.tsx` 覆盖对话框（使用数、派发的重命名、删除必经的确认、空看板）。`tests/protocol.spec.ts` 守线形，`tests/host-ledger.spec.ts` 通过真实账本应用两个动作（含 revision 前进与拒绝）。该流程也在真实宿主上端到端跑过：在管理器里做一次重命名与一次删除后，从 `$DSH_HOME/task-board/ledger-v2.json` 读回了结果。清理补在两层上：`tests/task-tag.spec.ts` 覆盖候选判定（低于阈值且卡片全部结算、恰好等于阈值、归档的已结算卡片放行、归档未完成的卡片留住标签，以及 `N` 的取值边界），`tests/tag-manager.spec.tsx` 覆盖这一行（无候选时的提示、确认框列出的清单，以及确认之前不派发任何动作）。

## Alternatives considered

**用既有的 `update` 动作逐张卡片改写。** 否决：被五十张卡片携带的标签意味着五十次往返、五十次 revision，中途失败会留下改到一半、且无法判断改了哪一半的看板。一个账本事务才是原子的，并且只给出一个结果。

**引入独立的标签注册表（一份标签清单，卡片引用 id）。** 否决：标签今天就活在卡片上，账本已经存在那里；注册表需要迁移，还要一套「卡片与注册表不一致」的对账规则。在用标签的并集是派生事实，不是第二个事实源。

**以「重命名为空名字」实现删除。** 否决：这会让空字符串成为重命名门禁的合法目标，而两个操作的确认方式与可逆性都不同。

**用下标或生成的 id 代替名字引用标签。** 否决：那样重命名仍要改写所有引用卡片，而名字才是用户输入、阅读与筛选所用的东西。

**重命名到已有标签时拒绝，而不是合并。** 否决：「这两个标签是同一件事」是常态（同一个错别字修了两次、一次导入用了另一种写法），拒绝会迫使用户先删掉一个标签——恰好丢掉合并所保留的那些提示。

**在线上新增一个批量清理动作。** 否决：`delete-tag` 本来就是每个标签一笔原子账本事务，批量动作要么在第二个入口后面逐标签重放同一条迁移，要么变成一种全有或全无的重写、并为它的中间状态额外解释。每个候选一笔迁移，每次移除都是一个管理器可以展示的独立提交结果。

**定时清理，或在看板打开时自动清理。** 否决：删除标签不可撤销，而自动执行恰恰在最没人看的地方出错——阈值设得激进就会抹掉没人注意的标签，而支撑这次删除的清单从未被人看过。由用户触发并确认的一遍，把损失摆在造成它的人眼前。

## Consequences

- 看板新增两个线动作。旧 bundle 对新宿主（或反之）会被严格协议门禁拒绝，而不是半途生效。
- `updatedAt` 只在真正被改动的卡片上推进，因此整账本重命名不会给归档区重新盖时间戳。
- 管理器是标签离开看板的唯一出口，清理也长在同一个对话框里，出口因此仍然只有一个；将来的批量标签编辑应扩展这个对话框，而不是长出第二个界面。
