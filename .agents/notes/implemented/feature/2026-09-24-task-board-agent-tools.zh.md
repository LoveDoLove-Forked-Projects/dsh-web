# Agent Note: 任务看板 Agent 工具

Status: implemented

## Problem

看板此前只能在 Web 界面操作。Host 已经拥有账本、cron 调度与执行 runner，插件也已通过系统提示词段向 agent 声明自身能力，但被要求「把它放到看板上」或「执行那张卡片」的 agent 只能让用户自己去点。所有看板操作——包括同一批交付的子任务关系——都无法从对话触达，于是 agent 能规划看板工作却无法真正执行。

## Decision

`src/host/agent-tools.ts` 定义八个面向模型的工具，插件激活后在看板启用期间把它们注册进工具注册表。它们绑定浏览器驱动的同一个 `TaskBoardHostService`，因此在界面创建的任务对 agent 立即可见，反之亦然，工具层不重复实现任何规则。这些工具暴露的父子层级规则归 [task-board-subtasks](2026-09-24-task-board-subtasks.zh.md) 所有。

### Tool surface

- `task_board_list`：按列、父任务、仅根任务、标签、自由文本与归档状态筛选，并返回看板摘要（revision、时区、子任务深度上限、会话默认权限、各列计数）。
- `task_board_get`：读取单张卡片全量信息——Prompt、标签、父任务链接、直接子任务、深度、执行目标、计划、权限门状态、续接卡片快照与交接包引用，以及最近十次执行（含会话 id、发起方与结果）。
- `task_board_create`：创建任务，或用 `parentId` 创建子任务；未设置的执行目标继承父任务，并适用深度门禁。
- `task_board_update`：修改内容、标签与执行目标；空字符串清除某个目标，空标签数组清除全部标签。
- `task_board_set_parent`：把现有卡片挂到父任务下，或用空 parentId 解除关联。
- `task_board_run`：立即执行一张卡片，或重跑已结算的卡片，并级联它整棵子任务树。
- `task_board_manage`：在待办与待规划之间移动卡片，归档、恢复或删除。
- `task_board_schedule`：启用、修改或关闭卡片的 cron 规则。

### Registration and failure tolerance

- 注册跟随 `enabled` 主开关：看板关闭时不响应任何工具调用，关闭动作在切换公告的同一条提交路径上释放工具注册。
- 工具注册表按可选服务解析而不写入 `inject`，与可选 `llm` 的解析方式一致：运行时不提供注册表的部署仍会挂载整个看板，只失去工具面。运行时提供作用域注入时，晚到的注册表会通过它被跟进。
- 工具调用经进程内服务而非浏览器 HTTP 栅栏驱动 Host，因此不存在需要同步的第二条传输通道；服务自身的 active 标志与账本门禁仍是唯一权威。

### Refusals and the human gate

- 领域拒绝以带 code 与 Host 消息的 `ok: false` 值返回，让模型自行纠正，而不是读到抛出的异常。
- 刻意不提供 `confirm-permission` 工具。该门禁存在的意义是由人工放行高于默认值的权限绑定；能自行盖章的 agent 会让这道门形同虚设，因此 `task_board_run` 改为回答 `confirmation-required`。工具面也无法转移确认：继承来的绑定始终留在祖先卡片上、在启动时解析，因此 agent 先创建再解除关联的子任务不会带走绑定或确认。
- 深度门禁、运行中任务锁、归档与删除护栏、失败即关闭的钉子都经界面使用的同一批账本 action 抵达，工具面无法绕过。

### Attribution

- 工具调用从执行上下文读取发起会话 id 并作为动作 initiator 传入，因此执行会把它记为 initiator，创建或更新会把写进续接卡片快照。
- initiator 始终只是审计元数据：界面动作由浏览器断言、这里的动作由调用 agent 断言，没有任何门禁依赖它。

## Alternatives considered

**工具内通过 loopback 调用看板自己的 HTTP API。** 已否决：这会引入第二条传输通道，牵入同源标记与代理 token 处理，并让一次本地函数调用因为与账本无关的原因失败。host 半区本就持有该服务。

**用一个带 action 枚举的复合工具覆盖全部操作。** 已否决：一个含二十个可选字段的 schema 比八个聚焦的 schema 更难被模型正确填写，而且额度与门禁这类安全说明只能挤进一段描述。本家族中的 ssh 工具面做了同样的选择。

**把 `tools` 写进 `inject`，让该行等待注册表。** 已否决：这会把「可选注册表缺失」变成插件挂载失败，而这正是本包通过可选解析 `llm` 所避免的失败模式。界面与执行都不依赖工具面。

**暴露 `confirm-permission` 让 agent 自行解封。** 已否决：该门禁是本包对高于默认权限的唯一人工闭环控制；能自己置位的 agent 不构成控制。

**把续接卡片创建（冻结快照与交接包）也做成工具。** 暂缓，未实现：这些载荷由会话自身的冻结块产生，且已可通过界面表单录入；给模型一个自由文本的冻结构造器只会扩大提示注入面，而看板并不缺这项能力。

**无条件注册工具，忽略 `enabled`。** 已否决：主开关的含义就是「看板不在运行」，界面隐藏时仍会应答的工具会成为第二个相互矛盾的事实来源。

## Consequences

- 对话现在可以消耗真实 API 额度：`task_board_run` 会开启真实会话，子任务树每个成员一个。
- 工具面为每个已启用 agent 的上下文增加八段简短描述，每段都写明触发词，包含中文看板词汇。
- 由于工具复用账本 action，agent 到达不了用户到达不了的状态：界面会给出的拒绝在工具面同样可达，每道门禁都照旧生效。
- 执行与编辑都归属到发起会话，因此看板审计可以区分 agent 发起的工作与界面点击。
- 必需验证：`tests/agent-tools.spec.ts` 覆盖构建与「刻意没有确认工具」、列表与详情投影、子任务创建与继承、深度拒绝、关联与解除关联、一次级联执行为每个成员开会话、`confirmation-required` 拒绝、发起方归属、归档与删除护栏、计划、局部更新，以及看板关闭时的拒绝；包内 `typecheck`、`test`、`build` 为门禁。
