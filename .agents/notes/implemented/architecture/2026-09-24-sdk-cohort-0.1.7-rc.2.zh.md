# Agent Note: SDK cohort 0.1.7-rc.2

Status: implemented

## 背景

集成分支声明的是 `0.1.7-rc.1`，而官方家族在 2026-09-24 发布了 `0.1.7-rc.2`（npm `next`，宿主 CLI 于 14:18Z 上线），距 rc.1 cohort 落地仅一天。按兵不动会让家族的机器可读下限指向一个在同一天就停止接收修复的宿主，而且这个候选版本的内容并非空变更：宿主新增依赖 `@deepseek-ai/dsh-experimental-auto-review`，Web 应用新增 `dsh-schedule`、`dsh-time-context`、`dsh-client-shortcuts` 与 `dsh-client-ui-shortcuts`，`dsh-client-ui-primitives` 还导入了一个其 manifest 仍未声明的面。

这次发布也是分两批到达的：SDK 包从 13:58Z 开始出现，宿主到 14:18Z 才上线，因此在那个窗口内做 cohort 检查会得到一个「半发布」的家族；检查必须重新查 registry，而不能凭 release tag 推断。

## 决策

整个 cohort 在隔离工作树 `sdk/0.1.7-rc.2` 中一次性迁到 `0.1.7-rc.2`，基线取本地 `dev` 顶端（`46ee2736`，领先 `origin/dev` 两个未推送提交），因此在整合之前共享 checkout 与运行中的 GUI 不受影响。这是该线上的第二次迁移，承接 [sdk-cohort-0.1.7-rc.1](2026-09-23-sdk-cohort-0.1.7-rc.1.md)：其记录继续拥有 rc.1 迁移，本记录拥有 rc.2，不取代前者。该基线带有 Electron 桌面端移除提交，这正是本次 cohort 迁移只有五个 host floor 面而非六个的原因（见下）。

### 一个 cohort，一个字面量

41 个文件、318 处 specifier：十五个家族 manifest、插件脚手架、shared 工作区包、`dsh.engines.dsh` 下限及其同字面量的 `@deepseek-ai/dsh` host peer、release-age 排除账本、re-key 到新 cohort 的两个 `packageExtensions` 键、根目录双语 README badge、CI 与 release 的挂载冒烟 pin、`shared/web-platform.ts`、`shared/tests/web-platform.spec.ts`、`tests/e2e/mount.e2e.ts` 与 `scripts/rollout-verify.test.mjs` 中的 cohort 字面量，以及 `docs/publish-prep.md`、`docs/plugins.md`、`packages/dsh-web-all/aggregate.yml` 和三个包 README 对（含重新记录的 pairing 记录）中的 cohort 表述。`@deepseek-ai/cordis`（4.0.4）与 `@deepseek-ai/schemastery`（3.18.4）不动：它们各自独立推进，且 cohort 自身的 peer 区间仍然约束它们。

### 两个面是对已发布产物实测的

- **冻结模块表未变。** 解包两个 cohort 版本的 `@deepseek-ai/dsh-web-frontend` 可以看到 `staticModules` 的九个 specifier 完全一致，只有压缩后的标识符不同。因此 `shared/web-platform.ts` 保留其列表，只改 provenance 注释。新的 `@deepseek-ai/dsh-client-shortcuts` 是被侧栏与工作区行注入的普通 client 插件，不是静态模块。
- **primitives 补丁新增一个面。** `@deepseek-ai/dsh-client-ui-primitives@0.1.7-rc.2` 导入 `@deepseek-ai/dsh-util-code-language`（该包在 rc.2 首次发布），而其 manifest 仍未声明任何运行时依赖。`packageExtensions` 条目补上了这个精确 pin。既有的上游打包缺陷（`dsh-client-store` 未声明 `immer`/`zustand`，`dsh-client-ui-primitives` 的长列表）在 rc.2 原样存在，因此没有删除任何补丁。

### 上游发布缺口与本次验证方式

`@deepseek-ai/dsh@0.1.7-rc.2` **无法从 npm 安装**。`@deepseek-ai/dsh-web-app@0.1.7-rc.2` 精确依赖 `@deepseek-ai/dsh-client-ui-settings-account@0.1.7-rc.2`，而该包上游从未发布（其 `next` 与最新版本都是 `0.1.7-rc.1`），因此 `npm install -g @deepseek-ai/dsh@0.1.7-rc.2` 与 CI/release 的挂载冒烟步骤都以 `ETARGET` 失败。这不是改名：`dsh-web-app` 在 rc.2 仍列出全部十一个 `settings-*` 行、没有删除任何一个，反而新增了四个包。宿主 81 个直接依赖全部可解析，缺的只是这一条传递边。

因此全局 CLI 停在 `0.1.7-rc.1`（npm 不会留下半装状态），依赖宿主的那几道门禁改用一个 scratch 宿主运行：装进临时前缀，只加一处有据可查的覆盖——把 `@deepseek-ai/dsh-client-ui-settings-account` 钉在 `0.1.7-rc.1`——再通过仓库自带冒烟 lane 的 `DSH_CMD` 开关接入。这足以在真实 rc.2 宿主上跑通本检出构建的插件，但不足以发布，因为发布管线安装钉住的宿主时不带任何覆盖。**在上游补发该包之前发版保持阻塞；本记录描述的是一次已验证、但尚不可发布的仓库侧 cohort 迁移。**

### Native-first 重叠清单

rc.2 的变更在动手适配之前已逐项对照家族。新增的官方能力是增量的，每个重叠候选都落在既有的薄扩展上：

| 官方能力（rc.2 新增或变更） | 本仓实现 | 决定 |
| --- | --- | --- |
| 插件页的自动审阅开关；Inspector 不再默认内置；官方源/镜像辨识；GitHub 安装失败时的镜像回退；插件详情修复 | `dsh-plugin-manager`（更新检查、冲突账本、修复交接、只读清单） | 按薄扩展保留、不改动。其 README 自 0.1.7-alpha.1 起就把安装、卸载与启停交给官方页面，自身只读渲染清单，因此 rc.2 改动的正是这个包刻意不占的面。不移除。 |
| 定时任务与提醒，含运行记录、重启保留、Web 端默认关闭 | `dsh-task-board` 的 Host cron 调度（对运行真实 DSH 会话的任务卡做五段 cron） | 保留。对象与账本不同：官方调度器管提醒，我们管任务账本并对其执行 agent 运行。不移除；「默认关闭」这一先例值得在产品评审中借鉴，不属于本次 cohort 迁移。 |
| 会话列表的归档筛选（隐藏已归档／全部／仅显示已归档） | `dsh-session-archive`（状态筛选、搜索、排序、批量归档/删除、自动策略），且已接管官方 `archived-sessions` section id（order 25） | 保留。官方筛选作用于侧栏会话与工作区列表，我们筛选的是本插件从 0.1.5 起接管的清单 section，两者读取的集合不同。登记为保留例外而非移除，因为移除我们的筛选会回退原生并不提供的批量管线。 |
| 快捷键（查看/搜索/自定义/重置） | 无 | 无重叠，无需移除 |
| 时间上下文间隔；Coding Tools 模式选择；账号/API Key 模型入口；审批卡语言 | 无平行实现 | 无重叠，无需移除 |

没有任何家族包实现了本 cohort 新增的能力，因此不删除任何实现、不回退任何能力。一处保留如实记录而非隐藏：上述三个「保留」决定依据的是官方变更记录与各包自身契约，实际只被验证到挂载冒烟所及深度（挂载、启动、无崩溃标记）。更深的逐面 GUI 对比——也就是一次移除所必须的证据——在宿主无法从 registry 安装期间无法取得。

### Host floor 面

[dsh-host-floor-tracks-cohort](2026-09-01-dsh-host-floor-tracks-cohort.md) 点名的六个面中有五个随迁移移动：engines 下限、host peer、根 README 双语 badge、CI/release 挂载 pin，以及 `docs/publish-prep.md` 的冒烟说明句。第六个——`desktop/runtime/host/package.json` 的桌面包体 pin——在本基线上已不存在，因为 Electron 桌面应用及其打包 lane 已在 `64beab4a` 移除；没有可移动的对象，它携带的一致性要求也随之退役。`pnpm-lock.yaml` 中记录的卫星 peer 下限仍是 `>=0.1.7-rc.1`：它们属于卫星包，由各自仓库在对齐版本发布时更新。

## 被否决的备选

**等缺包发布后再 bump。** 否决：cohort 迁移是仓库侧变更，其验证并不依赖缺失的那一行，压着分支反而让家族继续声明一个该线已经离开的下限。发版是单独设卡的环节，缺包真正咬人的地方在那里。

**0.4.2 先按 `0.1.7-rc.1` 发，rc.2 随后再补。** 被操作者否决：0.4.2 要带 rc.2 cohort，因此宁可让发布等待，也不发一个 SDK 已经取代的 cohort。

**在发布管线里覆盖缺失依赖。** 否决：管线按用户的方式安装钉住的官方宿主。在那里加覆盖会发出一个没有任何用户能复现的宿主组合，把上游缺陷藏在本地补丁后面。

**把 `@deepseek-ai/cordis` 与 `@deepseek-ai/schemastery` 一起移动。** 与上一个 cohort 同理否决：两者都没有发布 `0.1.7-rc.2`；各自线路独立，cohort 的 peer 仍然约束它们。

**既然官方 preflight 回答了同一个问题，就移除 `dsh-plugin-manager` 的兼容性预检。** 仍否决，与 rc.1 记录一致：两条规则读取的字段不同，而证明官方在 npm 发布的 web 运行时上确实拒装所需的 GUI 证据，在宿主装不上期间不可得。

## 后果

- 声明下限、host peer、badge 与 CI/release 挂载 pin 全部指向 `0.1.7-rc.2`，于是仓库声明的要求领先于用户实际可安装的版本。这是有意的过渡状态：它正是上游缺口造成的局面，此处如实记录而非掩盖。
- 0.4.2 的发版阻塞在 `@deepseek-ai/dsh-client-ui-settings-account@0.1.7-rc.2`。打 tag 前重试 `npm install -g @deepseek-ai/dsh@0.1.7-rc.2` 并重跑挂载冒烟即可，其余无需改动。
- 卫星包仍以 `>=0.1.7-rc.1` 声明 host peer。四个卫星仓库发布对齐后的 `0.4.2` 时它们自然收敛，而发版流程要求这一步先于本仓打 tag。
- 在全局 CLI 迁移并重启之前，本地 profile 的 `@deepseek-ai/*` 影子副本继续停留在 rc.1 cohort。CLI 装不上期间，profile 手术既不可能也非必需。

## 验证

在隔离工作树的提交树上运行：`pnpm typecheck`、`sync-shared:check`、`libs:check`、`build`、`test`、`test:scripts`、`runtime-deps:check`、`aggregate:check`、`emoji:check`、`test:standards`、`docs:check` 与 `i18n:check` 全部通过；锁文件重解析到 rc.2 后，`pnpm install --frozen-lockfile --ignore-scripts` 在 468 个条目上通过供应链策略。

`bash scripts/e2e-mount.sh` 以 CI 形态对 scratch rc.2 宿主运行（`DSH_CMD` 指向 scratch 安装，`FAMILY_TGZS_DIR` 指向本检出打包的 tarball）：聚合包经 `dsh plugin --profile web add` 挂载，`dsh web` 在 OS 分配端口启动，Playwright 无头 lane 通过——官方宿主帧完成挂载，且没有出现被排除的外部行。

以下未经验证，并在此明确记为缺口：钉住的宿主从 registry 安装、发布管线自身的挂载冒烟，以及三个「保留」重叠决定背后的逐面 GUI 对比。这三项都被缺失的 `@deepseek-ai/dsh-client-ui-settings-account@0.1.7-rc.2` 阻塞，而不是被本次变更阻塞。
