# Agent Note: Integrated Web Extensions settings parent

Status: implemented

## Problem

The family settings dialog assigns one first-level navigation row to every feature. Web plugin cards, skins, pets, the Workshop and usage therefore consume five rows even though their management pages belong to the same extension area, and the long skin, pet and usage pages make that navigation cost more visible. Merging them must not break standalone package installs, existing family card seats or links that open usage directly.

## Decision

`dsh-web-settings` owns the stable first-level `settings.section` id `web-ui-plugins`, displays it as Web Extensions, and declares the keyed/root `web-ui.extension` child seat. The parent renders only pages registered through its service, ordered by each page's declared `order`; Web Plugins, Skins, Pet, Workshop and Usage are default registrations rather than a fixed five-key table. The service owns their labels, the accessible top tab strip that wraps on narrow widths, and the active keyed mount. The Web Plugins page continues to declare `web-ui.plugin.item`, and the Workshop page continues to declare `dsh-workshop.panel`, so neither extension ecosystem moves.

The parent publishes `webUiExtensions` with `sectionId`, `label()`, `open(id)` and `registerPage(page)`. A page registration supplies its key, order, locale, label, inject face, component and any child slots; the service registers the matching keyed entry, tracks its disposer, sorts the TAB snapshot and remounts a page if its keyed entry disappears. Child plugins never register into `web-ui.extension` themselves through the integrated path. A shared fallback adapter keeps one page in either the service or the plugin's original first-level `settings.section`; it waits for the target declaration and reconciles when the parent loads or unloads, so the service-publication/declaration gap and declaration collapse never produce refused-registration retry loops. Form controllers belong to the plugin apply lifecycle rather than a seat, so migration does not reset drafts or subscriptions. `open(id)` selects the requested TAB before calling the native settings store on the stable parent id; the usage foot card retains its DOM-replay fallback with the parent id and label when native navigation is unavailable.

The usage page uses summary and trend grids, the skin page opens with the looks other plugins paint (Wallpaper Engine and the delegated skins) as cards side by side and continues as one flat column whose settings groups and library are divided by hairlines instead of boxes, and the pet page places visual pet choices beside grouped fields; all use narrow-container single-column fallbacks. Small N-choice controls on these pages use visible segmented groups with `aria-pressed`; the shared settings fields expose that presentation as an opt-in, leaving unrelated plugin cards on their compact select. Every segmented group, the parent's TAB strip included, marks the pressed option with one highlight that slides to it instead of repainting each option, and a TAB switch slides the leaving page out as the new one comes in. The parent heads its pages with the Web Extensions title and a link to the repository. The Web Plugins page is two titled groups, General (the telemetry switch as a plain row) and Plugins (the family cards). Inside a family card every field is one settings row: label and hint on the left, the control on the right, stacked when the card is narrow; a boolean field defaults to a segmented group.

The Pet, Workshop and Usage pages are one family card each: a page-level switch sits at the header's trailing edge, a switched-off page keeps only that header (plus the failure line when a write was refused, so the reason stays readable), the Workshop's kind tabs and the Usage page's own tabs ride the same segmented track as the parent's TAB strip, and the Workshop puts its search field and bulk install on one row. The Usage page's display rows close the card body (poll interval with a slider bubble, display currency as segments, the exchange rate only while spend shows in dollars), and the pet page groups its fields under Display and Bubbles. Every page's copy states what a setting does in one short sentence, in the manner of the Claude Style settings; a hint that needs its full explanation keeps it as the paragraph's tooltip. A settings row caps its control column at half the row width, so a three-option segment carrying a long localized label wraps inside the track instead of crushing the hint into one character per line. A family card has no save button. A pick (a segment, a select, a reset) is written the moment it is made; typed text is written once typing pauses, on Enter or when the field is left, and Escape puts the stored value back. A refused write puts a pick back to the stored value and keeps typed text so it can be corrected, and the card shows the failure as one line under its rows. A bounded number (a card field given a range, a skin-page stepper) raises a bubble with a slider over the whole range when the pointer rests on it: the value follows the thumb and is written once, on release. The pet page carries its own copy of the card and follows the same rules, its pet-API fallback included. Semantic plugin roots identify current pages for skin patches. First-level `nth-child` selectors are not a supported anchor because unrelated plugins can add or remove navigation rows.

## Alternatives considered

- Keeping independent first-level pages and only restyling their contents. Rejected: it does not reduce navigation growth or provide the requested shared extension hierarchy.
- Registering every feature permanently into a new parent without a service-gated fallback. Rejected: standalone skin, pet, Workshop and usage installs would lose their settings entry when the parent package is absent.
- Moving the existing family plugin cards or Workshop asset panels into the new keyed seat. Rejected: those seats have their own ownership and declaration lifecycles; preserving them avoids migrating unrelated contributors.
- Having every child register into `web-ui.extension` directly and keeping a fixed TAB table in the parent. Rejected: each child would need the parent's private mounting details, page metadata would be split between two registries, and adding a page would require editing the parent's hard-coded list.
- Keeping the card's Save / Discard footer. Rejected: a control that has visibly changed but has not taken effect, behind a button at the end of a long card, reads as applied when it is not; applying at once follows the Claude Style settings this layout is modeled on.
- Retaining positional navigation icons and illustrations. Rejected: the real settings navigation also contains third-party sections, so a position does not identify a feature. The parent uses the native fallback icon and semantic panel roots drive page-specific skin decoration.

## Consequences

- A full family install exposes one Web Extensions row with five secondary TABs; an individual content package without the parent keeps its original first-level row and id.
- Existing `web-ui-plugins` deep links remain valid. Usage navigation additionally selects its TAB before opening that section, including the pending selection left for DOM fallback.
- Only the active keyed page polls or renders its detailed content. Switching seats disposes the old registration before creating the replacement, with a re-entrancy latch for synchronous slot events.
- `packages/dsh-web-settings/tests/web-extensions-section.spec.tsx`, `web-ui-extensions.spec.ts`, `packages/dsh-market/tests/extension-seat.spec.ts`, `packages/dsh-usage/tests/section-integration.spec.ts` and the satellite seat suites pin TAB behavior, deep-link order and standalone/integrated migration; `packages/dsh-remote-web-ui/tests/immediate-apply.spec.ts` and `packages/dsh-task-board/tests/settings-card-text-commit.spec.tsx` pin when a card writes.
