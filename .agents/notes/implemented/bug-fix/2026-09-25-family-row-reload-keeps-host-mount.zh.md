# Agent Note: 重新加载后的家族行保留其 Host 半区挂载

Status: implemented

## Problem

聚合包为每个家族插件挂一行 loader 条目，在[聚合 shell](2026-09-01-aggregate-plugin-fault-isolation-shell.md)
后面挂载真实插件包；共享的 `mountOnce`（`shared/host/mount-once.ts`）让聚合行与
同一包的独立安装能在同一进程共存：首次挂载正常执行，之后同名包的挂载成为空操作，
持有者的 fiber 销毁时释放该名字。

空操作只在持有者仍存活时才是安全的。宿主重载 profile 的顺序是「先创建新的 loader
条目、再销毁旧条目」——插件管理器每次启用/禁用/安装写入触发的 profile 重载、
`cordis.patch.yml` 的 HMR 重载、以及设置项触发的行重挂载都落在这个顺序里。
此时重新加载的 shell 条目请求同一个包名，而旧条目仍持有它，于是这次挂载被丢弃；
片刻后旧条目销毁自己的挂载，名字空出来却再没有人接手。结果是：家族行仍被列为
active、degraded 账本为空（没有任何异常抛出，shell 的隔离账本无失败可报）、宿主
路由全部消失。在 dsh-app 桌面上，任务看板的 `/api/task-board/*` 收到 webserver
的纯文本 `not found`，面板在空看板上渲染 `board.hostError.notMounted`，只有重启
Host 才能恢复。账本 30 秒一次的调度心跳恰好停在重载那一刻，这条证据把丢失定位到
重载本身，而不是一次挂载失败。

## Decision

`mountOnce` 保持单实例保证，并且不再丢弃被拒绝的挂载：

- 当另一个 fiber 持有包名时，被拒绝的挂载连同它自己的 context 与 config 一起排入
  该持有者的等待队列，并在持有者释放名字时重放。重放推迟一个微任务执行，好让正在
  销毁的挂载先拆掉自己的效果（webserver 路由、账本、定时器）。重放会重新进入守卫，
  因此期间到达的挂载仍然去重为恰好一个存活实例。
- 等待者自己的 fiber 在释放前销毁时，它从队列中移除且永不重放：它的 context 已经
  消失，在其上注册效果会抛错。
- 名字仍由持有者自己的 disposer（守卫注册的 fiber 级效果）释放，释放后按到达顺序
  交接给队列。

守卫的所有权规则不变：每个包名恰好一个存活挂载，聚合行与独立安装依旧不会重复注册
路由、工具、settings 命名空间或 system-prompt 段。

## 跨仓库注册表契约

`Symbol.for('dsh-web.mounted-plugins')` 是本仓库并不编译的那些构建共享的契约：
四个卫星包（dsh-skins、dsh-pet、dsh-presets、dsh-community-plugins）是独立仓库，
各自带着这份守卫的副本并自行安排重建。因此该键下的值保持所有已发布副本都会读的
形状——包名的 `Set`，使用 `has`/`add`/`delete`——而本次新增的等待队列放在
自己独立的附加键下：`Symbol.for('dsh-web.mounted-plugins.waiters')`，类型为
`Map<string, PendingMount[]>`。共享键上出现的异形值（过渡期的形状、被手工写入的
全局）会被替换成全新的 `Set`，而不是被当作集合读取。

本修复的第一版把 claim 映射直接写进共享键。这一形状变更正是本节要防止的错误：
所有卫星仍写入 `Set`，于是在卫星先挂载的进程里，家族副本把 `Set` 当 `Map` 读，
其后挂载的每一行都以 "claims.get is not a function" 降级——现场表现为
model-capabilities 与 remote-web-ui 两行失败、路由消失，比被修的缺陷本身更糟。
附加键让「重放行为」与「跨仓库契约」彼此独立。

## Testing

`shared/tests/mount-once.spec.ts` 钉住重放、被放弃等待者路径、多个等待者争抢一次
释放时仍只有一个存活挂载，以及包之间互不影响的既有行为。
`packages/dsh-web-all/tests/shell-reload-mount.spec.ts` 用真实 cordis context 驱动
真实 shell 源码与一个家族行替身：挂载该行、在旧条目仍存活时挂载重载后的条目、销毁
旧条目，然后断言该行仍在提供自己的路由，且最后一个条目销毁时仍会拆除它。该测试在
修复前的实现上失败（销毁后的路由断言 `expected false to be true`），这就是本记录
所钉住的回归。另有两条共享用例钉住跨仓库契约：旧副本写在共享键上的 `Set` 会被尊重
而不是当作 map 读取；共享键上的异形值会被修复，而不是让之后每次挂载都失败。

## Alternatives considered

「在聚合 shell 内部重试」被否决：shell 看不到别的条目的挂载，而 13 个包共用这个
守卫，契约应当留在包名被拥有的地方。「彻底移除 `mountOnce`」被否决：聚合行与同一
包的独立安装会重复注册路由、工具与设置并导致启动失败，这正是守卫存在的理由。
「在持有者销毁开始时提前释放名字」被否决：释放必须排在该挂载自己的路由与账本拆除
之后，否则两个挂载会瞬间重叠；而队列让具体顺序变得无关紧要。「在 disposer 内同步
交接」出于同一理由被否决——在拆解中途重放会在旧路由仍在时注册新路由，正是聚合包
曾经踩过的重复路由故障。

## Consequences

在旧条目仍存活时被重载的家族插件现在能继续服务：profile 写入之后，宿主不再需要
重启才能让任务看板、市场、git 图谱等家族 Host 半区回来。重放会在重载条目的
`apply` 解析完成之后才注册插件效果，shell 自身的记账本就容纳这种情形（延后的效果
属于同一个 fiber，随之销毁），`packages/dsh-web-all/src/shell.ts` 的路由决策无需
改动。若某进程终生同时持有同一包的两个来源，被拒绝的挂载会作为队列等待者保留
（每行一个闭包）而不是被丢弃；这就是「永不丢失挂载」的代价。

卫星包无需重建即可与新的守卫共存：它们读取的共享键保持原形状，而新增的队列键只有
新副本会读。由变更前的副本持有的包名依旧不会被重复挂载，但那个旧持有者的释放不会
排空新队列，因此仅被「变更前持有者」拒绝的挂载会一直留在队列里，直到该名字再次被
接管——这一组合会在该包重建后消失。
