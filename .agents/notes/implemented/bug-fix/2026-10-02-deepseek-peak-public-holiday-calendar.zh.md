# Agent Note：DeepSeek 峰谷规则把法定节假日按空闲计费，因此本包自带节假日表

Status: implemented

## 问题

报告的症状是估算价约为实际价的两倍，归因是「调休上班的周末」被按空闲计费。排查确认 [峰谷计价笔记的时钟](../implemented/feature/2026-08-29-usage-peak-pricing-and-announce-fix.md) 确有缺陷，但**误差方向与报告相反**：偏差出现在法定节假日（估算偏低），而周末本来就已按提供方的口径处理。

官方规则（[api-docs.deepseek.com 价目表](https://api-docs.deepseek.com/quick_start/pricing/) 脚注 2）：高峰时段为北京时间周一至周五 09:00-12:00、14:00-18:00，**不含中国法定节假日**；其余时段为空闲，**周末与法定节假日全天均按空闲**。

- **法定节假日无法从任何规则推导。** 国务院办公厅每年发布安排，日期逐年变化。原时钟只判 `getUTCDay()`，于是每个周一至周五都算高峰，包括按半价计费的节假日——这才是报告中真实存在的那一半。
- **调休上班的周末不是高峰日。** 提供方按自然日计费，不看工作安排：被指定为工作日的周日全天仍是空闲。原有的 `weekday >= 1 && weekday <= 5` 判断已经符合这一点，钉住它的测试正是防止日后有人「修复」出一个方向相反的错误。

## 决策

1. **规则把日期作为 `PublicHolidayCalendar` 接收**（`isPublicHoliday(date)`，北京时区 `YYYY-MM-DD` 字符串）。高峰判定与下一个边界扫描统一走一个 `isPeakDay()` 谓词，跳过节假日时不会留下幽灵时段。`YYYY-MM-DD` 是正确的粒度，因为节假日全天按空闲。
2. **默认日历就是公布的节假日表**（`src/core/holidays.ts`），覆盖 2020 至 2026 年。此前的默认日历为空，缺陷因此不可见；接入表之后，节假日的工作日无需调用方传参、无需在折叠处接线，即按空闲档计价。
3. **调休上班日刻意不进表。** 只取来源数据中的 `holiday` 条目。被指定的周六周日按自然日即为空闲，列入反而会被算成高峰——正是本 note 要防的那个错误。
4. **表未覆盖的年份按工作日高峰计。** 此时估算偏高而非偏低，是更安全的误差方向：绝不会少报消费。

## 数据来源

表由 [bastengao/chinese-holidays-node](https://github.com/bastengao/chinese-holidays-node)（MIT）的年度数据 `data/<year>.json` 生成。

只内置数据文件。该包的运行时代码走网络请求，并引入 `request`（已弃用、存在已知漏洞）与 `moment`，没有 TypeScript 类型；`holiday-cn` 则是托管微服务而非库。这些都不该进入一个浏览器 bundle 受纯度门禁约束的本地费用账本。直接取年度 JSON 运行期零成本，且保持包本身零依赖。

更新方式：把新年份 `data/<year>.json` 的 `holiday` 条目重新抽取进 `src/core/holidays.ts`，并递增 `HOLIDAY_TABLE_LAST_YEAR`。测试会在年份不连续时失败，因此漏掉一年不可能悄悄通过。

## Context & Efficiency Impact

日历是对静态对象的一方法接口，host 半区每次折叠只多一次属性查找与一次 `includes`，浏览器半区除此之外无额外开销。表在源码中约 5 KB。无 schema、wire 或 prompt 成本；接口只在 `src/core/` 内部。

## 备选方案

- **把调休上班日当作高峰日（即报告原文的说法）。** 依据证据否决：提供方把落在周末的指定工作日全天按空闲计费。照此实现会让估算离账单更远，而且更难被发现——节假日比周末稀有。
- **硬编码某一年（如 2026）的节假日表。** 否决：会悄悄过期。覆盖年份连续且带覆盖测试的表，好过一张看似权威却落后一年的表。
- **运行期联网取节假日。** 否决：浏览器 bundle 纯度门禁不允许任意运行时请求；会随网络可用性静默变化的估算也不是确定性的费用记录。
- **引入第三方节假日依赖。** 否决依据是证据而非原则：可选的包要么就是数据源本身（联网、`request`、无类型），要么是托管服务。内置数据可以达到同样效果且无运行期依赖。
- **从农历推导节假日。** 否决：农历日期只有在国务院公布偏移决定之后才对应公历节日，那不是规则，而是第二套要维护的历法。

## 验证

`tests/pricing.spec.ts`：2026 年国庆假期内的周一与周四在**不传日历**时按空闲档计价，同一周的普通工作日按高峰档计价，并钉住调用方传入的日历仍可覆盖内置表。`tests/holidays.spec.ts` 检验表本身：2020 至 `HOLIDAY_TABLE_LAST_YEAR` 覆盖连续、无重复日期、每个日期都是可回环的 `YYYY-MM-DD`、不含调休上班日，以及未覆盖年份返回 false 而非报错。

## 风险

- **2026 年之后表会过期。** 超出表的年份按高峰档计价，会高报消费。这是有意选的失败方向，而覆盖测试就是发现它的位置。
- **错误的表比没有表更糟**：把普通工作日误标为节假日会低报繁忙日。因此才有普通工作日的断言，也因此只取上游公布的数据而非手工编辑的清单。
