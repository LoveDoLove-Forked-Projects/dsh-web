# Agent Note：市场的单文件体积上限会在部署时才拦下过大的皮肤

Status: implemented

## 问题

2026-09-30 这一轮皮肤收录把五个 PR 合进了 dsh-skins 卫星仓，并按惯例在本仓用两步上架：把 submodule 钉版移到卫星仓新的 main tip（`0fd62f6` -> `ec4ed25`）、重建 `market/dist`、推 dev。`market:check` 与 `test:scripts` 都是绿的，本地构建也没报任何问题。随后部署车道在 `wrangler deploy` 里失败：

```
[ERROR] Asset too large.
  Cloudflare Workers supports assets with sizes of up to 25 MiB.
  We found a file .../market/dist/assets/skins/rainy-night.zip with a size of 31.5 MiB.
```

商店把每套皮肤当作一个 zip 资产分发，而 Cloudflare Workers 对单个资产的上限是 25 MiB（26,214,400 字节）。`rainy-night.zip` 是 33,027,261 字节，因为这套皮肤带一个 32,494,969 字节的背景视频。仓库里没有任何地方写明这条上限：[market-build](../../../../scripts/market-build) 只校验安装器的 `MAX_FILES_PER_ASSET`（文件条数），没有字节体积门禁，所以超限资产能通过本地与 CI 的所有检查，直到钉版已经在 dev 上才失败——而这时候失败会挡住该分支后续每一次市场部署，因为路径过滤盯的正是同一批钉版。

## 决策

这次上架选择回退，而不是打补丁绕过。回退把钉版移回 `0fd62f6` 并还原 `market/dist`，部署车恢复绿色（run 36717073370），同时在 dsh-skins#16 上请贡献者重烤循环视频，让 zip 留在 25 MiB 以内。本轮另外四个合并留在卫星仓 main 上，等重烤到位后用同一个提交重新上架；在此之前商店继续提供旧内容，与部署失败期间的状态完全一致。

## 被拒绝的替代方案

- **恢复同一 PR 在最终提交之前烤出的 16,549,139 字节版本，整轮照原样上架。** 拒绝。这是替贡献者决定他们自己内容的烘焙版本，而且他们按实测写下的来源说明描述的是被撤下的那一版，维护者还得连带重写他们的记录。
- **照常上架，让部署一直失败到上游把资产压小。** 拒绝。dev 上的市场车道长时间飘红会挡住其它会话的所有市场工作，而上架的完成判定就是车道跑绿。
- **给 market-build 加一条字节体积门禁，超限的皮肤直接跳过。** 本轮拒绝。把已经合并的目录条目悄悄丢掉属于产品决策，这条门禁应该连同自己的测试单独成一次改动，而不是塞在一次上架修复里。

## 影响

- 商店内容保持不变：本轮另外四个合并（meridian、rainy-night 的同类与桌面端画框修复）要等重烤落地后才在本仓发布，重新上架只需一个提交。
- 内容上架只有在部署车道跑绿之后才算完成，所以携带大体积媒体的皮肤必须在合并闸门里就过掉车道的单文件上限，而不是在之后才发现；上限看的是发布 zip 的大小，不是源文件的大小。
- `market-build` 目前仍没有字节体积门禁；下一轮应考虑补上，让这类失败在钉版移动之前就暴露。
- [创意工坊改为 dev 推送即部署](2026-08-25-workshop-deploys-from-dev.md) 拥有该车道的触发与门禁；本记录只记平台侧强加给这条车道的约束。
